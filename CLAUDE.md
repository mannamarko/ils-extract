# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A set of standalone Node.js scrapers that extract every content type from ilshospitals.com (a WordPress site) into JSON — blog posts, taxonomies, departments, doctors, key procedures, health packages, hospitals, events, OPD schedules, FAQs, testimonials, job postings, CSR initiatives, the photo gallery and the gallery CPT behind it — together with a full SEO/JSON-LD audit of each page. There is no build, no test suite, and no framework: each `ils-*-scraper.js` is a CLI entry point run directly with `node`.

## Commands

```bash
npm install                       # axios, cheerio, puppeteer

# Content-type scrapers (each writes its own JSON to CWD)
node ils-blog-scraper.js --out ils_blogs_v2.json     # 465 posts (47 listing pages)
node ils-taxonomy-scraper.js                          # ils_categories.json + ils_tags.json
node ils-department-scraper.js                        # 60  -> ils_departments.json
node ils-doctor-scraper.js                            # 375 -> ils_doctors.json
node ils-key-procedure-scraper.js                     # 173 -> ils_key_procedures.json
node ils-disease-scraper.js                           # 50  -> ils_diseases.json (`disease` CPT; diseaseList.md lists only 31)
node ils-health-package-scraper.js                    # 35  -> ils_health_packages.json
node ils-hospital-scraper.js                          # 5   -> ils_hospitals.json (npm start)
node ils-event-scraper.js                             # 34  -> ils_events.json
node ils-opd-scraper.js                               # 374 -> ils_opd_schedules.json (166 with timings)
node ils-faq-scraper.js                               # 9 categories / 14 Q&A + 21 standalone -> ils_faqs.json
node ils-testimonial-scraper.js                       # 68 -> ils_testimonials.json
node ils-career-scraper.js                            # 29 -> ils_careers.json
node ils-csr-scraper.js                               # 13 -> ils_csr.json
node ils-gallery-scraper.js                           # 85 images, single page -> ils_gallery.json
node ils-gallery-post-scraper.js                      # 85 -> ils_gallery_posts.json (the `gallery` CPT, NOT the page above)
node ils-press-media-scraper.js                       # 97 -> ils_press_and_media.json
node ils-publication-scraper.js                       # 3 -> ils_publications.json
node ils-times-scraper.js                             # 7 -> ils_times.json
node ils-about-us-scraper.js                          # 10 members + 26 awards -> ils_members.json, ils_awards.json, ils_about_us.json
node ils-tieup-scraper.js                             # 25 corporate + 38 insurance/TPA -> ils_tie_ups.json (+ ils_tie_ups_corporate.json, ils_tie_ups_insurance.json, ils_tie_up_list.json)
node ils-sitemap-scraper.js                           # 26 categories / 1882 links, single page -> ils_sitemap.json

# Render scraped posts/departments back to HTML for eyeballing
node export-html.js --in ils_blogs_v2.json --out export
node export-html.js --slug some-post-slug
```

Common flags on every scraper except the hospital one:

- `--from-cache` — reparse the on-disk HTML in `.cache/`, zero network. **Use this while iterating on parsing logic**; a cold full run of the larger scrapers takes 10+ minutes because of the 800 ms politeness delay.
- `--refresh` — re-fetch everything and overwrite the cache.
- `--slug <slug>` / `--limit N` — narrow the run to one or a few pages (the closest thing to a single test).
- `--from-list <file>` — drive the detail pass from a previously written index file.
- `--index-only` — doctors/procedures/packages/events/opd/faq/testimonials/career/csr/press/tie-up/gallery-post: run pass 1 and stop, writing just the small index file (`doctors.json`, `key_procedures.json`, `health_packages.json`, `events.json`, `opd_schedules.json`, `faqs.json`, `testimonials.json`, `careers.json`, `csr.json`, `press_and_media.json`, `tie_ups.json`, `gallery_posts.json`).
- `--no-standalone` — faq only: skip the `faq-question-answer` posts, keeping just the 9 `/faq-lists/` categories.
- `--no-hospital-check` — tie-up only: skip pass 2b, the five `/hospital/<slug>/` fetches that prove the per-hospital insurance carousel is identical everywhere.

`ils-gallery-scraper.js` and `ils-sitemap-scraper.js` are the other odd ones out alongside the hospital scraper: each is a single static page with no CPT, index, or detail pass, so they only take `--out`/`--from-cache`/`--refresh` — no `--slug`, `--limit`, `--from-list` or `--index-only`. The sitemap scraper adds two of its own: `--no-xml` (skip the `/sitemap.xml` cross-check) and `--no-dataset-check` (skip diffing each section against the `ils_*.json` another scraper already wrote).

## Architecture

### `scrape-lib.js` — shared plumbing

Everything site-agnostic plus the SEO extractor lives here: `fetchHtml` / `fetchJson` (retry + backoff + on-disk cache), `extractSeo`, `extractJsonLdSchemas`, `normalizeHtmlWhitespace`, `slugFromUrl`. `cacheMode` is a mutable singleton that each script's `main()` sets from its CLI args before any fetch — that is how `--from-cache` / `--refresh` reach the fetch layer.

`ils-hospital-scraper.js` predates the library and has its own inline `extractSEO`/fetch. It is the odd one out; the other six all go through `scrape-lib`.

It also makes one extra fetch before its five: **the unit's icon image and its state exist nowhere on `/hospital/<slug>/`** — only in the homepage's location carousel, where each `div.location-tab` is an `<img>` plus `<p>City <br><span>State</span></p>`. The join key is the slug inside that tab's `openCity(event, 'hosp-<City>')` onclick, lowercased; do **not** join by icon filename (raipur's is `hospital-icon-raipor.jpg`). The server renders exactly 5 tabs — a saved/rendered copy of the page shows 13 because owl-carousel adds `.cloned` items at runtime, so `scrapeHomeLocationTabs()` dedupes by tab id regardless. The results land on each record as `city` / `state` / `icon_img` / `home_tab_id`, and a failed homepage fetch leaves all four null rather than aborting the run.

### The cache is the substrate

`.cache/<kind>/<key>.html|json` (gitignored) holds the raw response body for every page ever fetched: `posts/`, `listing/`, `departments/`, `doctors/`, `key-procedures/`, `health-packages/`, `events/`, `event/`, `opd-schedules/`, `faqs/`, `faq-lists/`, `testimonials/`, `testimonial/`, `category/`, `tag/`, `career/`, `job/`, `csr/`, `gallery/`, `press-and-media/`, `tie-up/`, `tie-up-list/`, `sitemap/`, `api/`. `gallery/` holds both scrapers' pages — the static page as `_page`, the 85 CPT posts under their own slugs, which never collide. Parsers are pure functions of these files, so re-running with `--from-cache` after a parser change is cheap and deterministic.

`ils-taxonomy-scraper.js` **hard-depends** on `.cache/listing/` existing — it derives post↔term membership by re-walking the cached blog listing pages, and throws if the blog scraper has not run.

### Two-pass pattern

Doctors, procedures and packages all follow the same shape: pass 1 parses a single server-rendered listing page (which is the *only* source for some fields — hospital availability via `hospital-<id>` CSS classes on packages, department/hospital ids via `data-speciality` on doctor cards, parameter counts and prices on package cards) and emits a small index file; pass 2 visits each detail page for body content, cross-references and SEO. WP REST (`/wp-json/wp/v2/...`) supplies post ids and dates.

`ils-career-scraper.js` follows the same shape for the same reason: hospital availability for a job posting (postmeta `show_in_hospitals`) is never REST-exposed, so it only exists as `hospital_<id>` CSS classes on each `.job_card` div on the single `/career/` listing page (department is `dept_<id>` classes there too, though that one *is* also available from the `job-departments` REST taxonomy). The id -> hospital name map comes from that same page's `#hospital_dropdown` `<select>`.

### Dataset join order

The datasets reference each other by WordPress post id, so scrape in this order:

`departments → opd → doctors → key procedures`

`ils-doctor-scraper.js` reads `ils_departments.json` and, when present, `ils_opd_schedules.json` (folding each unit's `timings` into the matching `hospital_availability` entry by doctor id + hospital id); `ils-key-procedure-scraper.js` reads both `ils_departments.json` and `ils_doctors.json`. All degrade to a warning (unresolved ids / empty `timings`) if the file is missing, so any scraper still runs standalone.

`ils-event-scraper.js`, `ils-opd-scraper.js`, `ils-faq-scraper.js`, `ils-testimonial-scraper.js` and `ils-csr-scraper.js` stand alone. OPD schedules are NOT on their own detail pages — `/opd-schedules/<slug>/` 302-redirects to the listing, which reuses the `/doctors-list/` `li.doctorCard` markup and embeds the schedule inline (`.opd-table-tabs` / `.opd-timing`). Events mirror the academia `course` pages (`.csr-sec-item` cards → `/event/<slug>/` detail with `section.csr-sec-for-page`) — CSR is in fact the post type those theme classes are *named* for; events and CSR just share templates. Unlike `/events/`, the `/csr/` hub does not paginate (all 13 cards render on one page; `/csr/page/2/` 500s), so `ils-csr-scraper.js` fetches it once rather than walking `/csr/page/N/`. FAQs live in **two** unrelated post types: `faq-lists` (the 9 categories the `/frequently-asked-questions/` hub links to, each a `.faq-accordian-box` accordion of sibling `.faq-question`/`.faq-answer` pairs — 14 pairs in all, and REST exposes no content for them so the HTML is the only source) and `faq-question-answer` (21 standalone Q&As with question = title, answer = content, both straight from REST; these are the randomized FAQ cards the department scraper skips). Testimonials (`testimonial` CPT, 68 items, no pagination) are the odd one out for linking: the `/testimonial/` listing cards have **no href at all**, so WP REST is the *only* route to a detail URL — there is nothing to join by slug. Detail pages embed either a YouTube (47) or Facebook (21) video behind the same broken-markup pattern (see below).

`ils-press-media-scraper.js` also stands alone, and is the one CPT whose cards do **not** link to a detail page: the `/press-and-media/` hub renders the same `.csr-sec-item` markup as CSR/events, but each card's anchor is either an `a[data-lightbox]` pointing at the featured image itself (80 "clipping" scans of newspaper coverage — the card *is* the content) or an `a[target="_blank"]` pointing off-site at the publication (17 "external_article"s, whose href is the post `content` pasted verbatim, trailing `\n\n&nbsp;` and all). So the card carries no slug, no id and no back-link, and the join to WP REST is **by featured image**: card `<img src>` == the media `source_url` (all 97 are distinct; one batched `/wp/v2/media?include=` call resolves them). `/press-and-media/<slug>/` does resolve 200, but it only swaps the `<title>`, banner `<h2>` and breadcrumb leaf and then re-renders the entire 97-card listing as its body — pass 2 visits it for the SEO block and records `detail_page_renders_full_listing` rather than re-parsing those cards.

`ils-sitemap-scraper.js` is the one scraper that reads *across* the others. `/sitemap/` is a single `page-template-footer-bottom-page` page whose body is one AIOSEO block — `div.aioseo-html-sitemap` with 26 `div.aioseo-html-<type>-sitemap` children (interleaved with `<br>`), each `h4` category + flat `ul > li > a`. The markup is unusually clean: all 1882 `<li>` carry exactly one `<a>`, no nesting, no empty link text, no external hrefs, **zero duplicate URLs**. So category / link text / order are recorded 1:1 — per-section `position`, page-wide `global_position`, and an `entries_flat` mirror in pure document order — and nothing is deduplicated or re-sorted. Section order is AIOSEO's registration order (Posts, Academia-List, Pages, Academia, Events, …, taxonomies last), preserved rather than normalized. What the sections *are* is the audit: **"Posts" lists 3 placeholder stubs** (`/blog-1..3/`) while the 465 real `/blog/…` posts are absent from the HTML sitemap entirely; **"Gallery" is a CPT** (85 `/gallery/<slug>/` posts, now `ils_gallery_posts.json`), a different post type from the photo page `ils_gallery.json` scrapes — though the two render the same 85 images, see the gallery paragraph above; **"OPD Schedules & Appointments" is per-*department*** (229 URLs, duplicate display names disambiguated by `-2`/`-3` slugs), not the 374 per-doctor records in `ils_opd_schedules.json`; **"Academia-List" is three datasets in one CPT** (courses + ILS Times + publications) plus a live `/academia-list/test/` stub. `dataset_audit` diffs each section against the dataset another scraper already wrote — by URL set where the URL spaces match, by count where they don't (hospitals/gallery/opd/academia-list, each carrying a `note` saying why) — and degrades to `dataset_missing` per section, so it still runs standalone. `/sitemap.xml` is **not** AIOSEO's: it is a stale third-party dump ("created with Free Online Sitemap Generator xml-sitemaps.com") that disagrees in both directions (775 HTML-only, 148 XML-only), reported under `xml_audit` with neither side treated as truth.

**"Gallery" is two things wearing the same name, and there is one scraper for each.** `/gallery/` is a single static `page-template-gallery` page; `/gallery/<slug>/` is a WordPress CPT of 85 posts. `ils-gallery-scraper.js` covers the page and has nothing to join — no WP REST call, no listing/detail split, no index file: one fetch, parse the flat grid of `div.gallery-card > a[data-lightbox] > img`, done. `ils-gallery-post-scraper.js` covers the CPT.

They are not unrelated, though: **the static page IS the CPT's archive**, rendered by featured image, and the two datasets are a verified bijection — 85 cards ↔ 85 REST posts ↔ 85 sitemap URLs, the card `src` set and the featured `source_url` set identical with zero delta either way. So the join is **by featured image**, press/media- and awards-style, never by title: the card's `data-title` *is* the post title verbatim, but titles duplicate (two posts titled "Cathlab", slugs `cathlab` / `cathlab-2`), so a title join silently collapses them. **One image is shared by two posts** — `featured_media: 16536` backs both `…-raipur-6` and `…-raipur-14`, which is why the page renders 85 card rows over only 84 distinct srcs and why the batched media call returns 84 records for 85 posts; src → post is 1:N for that one pair, resolved by walking the page's cards in document order and consuming each src's posts in REST order, and flagged `featured_image_shared_with_sibling` on both. REST exposes **no `content` and no `excerpt`** for this CPT (as with `faq-lists`) — the fields are absent entirely and `acf` is `[]` on all 85. The detail page is the **blog** single template reused with no body copy: a hardcoded "Home - Blogs - `<title>`" breadcrumb (a `/blog/` link on a gallery post, wrong on all 85, like the job pages'), the featured `<img>` byte-identical to the media `source_url`, `ILS Editor` + the publish date, and a `.blog-para > h3` that is the title *again* and nothing else — hence `breadcrumb_points_to_blog` / `no_body_content` / `title_duplicated_in_heading` on every record. The `.col-lg-3` sidebar is byte-identical on all 85 (the three lorem-ipsum `/blog-1..3/` stubs plus `category-1`/`category-2`), so it is lifted out of the records into a single top-level `blog_sidebar_boilerplate` and only fingerprinted per page. Both cross-checks — `sitemap_audit` against `ils_sitemap.json`'s "Gallery" section and `gallery_page_audit` against `ils_gallery.json` — degrade to a warning when the file is missing, so the scraper still runs standalone.

`ils-tieup-scraper.js` also stands alone, and is the one scraper whose two halves come from **different sources on the same page**. `/tie-up/` renders `#corporateTieUps` (5 pill tabs → panes `div#corpTab1..5`, one per unit, 27 cards / 25 distinct names) and `#insuranceTieUps` (one flat list, 38 cards) in identical `ul.com-logo-ul-f-start > li > img + p` markup — but only the insurance half is the `tie-up-list` CPT. The join is **by featured image** (card `<img src>` == media `source_url`), press/media-style: all 38 insurance cards resolve, **0 of 27 corporate cards do**, so corporate records carry no post id, slug, date or detail page and the hub HTML is their only source (title joins would be worse than useless — the page writes `NTPC(National Thermal Power Corporation)` where the CPT writes `NTPC – National Thermal Power Corporation`). Only 38 of the CPT's 62 posts render anywhere; the other 24 — a superseded corporate list plus Ayushman Bharat/CGHS/ECHS/CRPF/GAIL/MMTC/NFR/THASP — carry no hub placement. Hospital ids come from the page's Salesforce lead form (`select.form-hospital-item option[data-id]`), not the `#hospital_dropdown` / `#hospitalFilter` / `filterCheckbox` controls the other scrapers use; the pill labels match those option texts exactly, which is what makes the tab → id join work without a hardcoded map. `/tie-up-list/<slug>/` 200s on the **blog** template with no body copy and a "Home - Blogs - `<name>`" breadcrumb, so pass 2 takes its SEO block and records `detail_page_has_no_body_content` + `breadcrumb_points_to_blog`. Pass 2b fetches the five `/hospital/<slug>/` pages purely as evidence for the gotcha below.

Besides the combined `ils_tie_ups.json`, the scraper also writes three split files. `ils_tie_ups_corporate.json` and `ils_tie_ups_insurance.json` carry the same enriched per-kind records the combined file's `corporate`/`insurance` arrays do (name, hospitals, CPT match, logo, `detail`/`seo`/`seo_issues`, issues), just on their own — the insurance file also carries `hospital_insurance_carousel`. `ils_tie_up_list.json` is a different thing: the `tie-up-list` CPT itself, all 62 posts, each tagged with `appears_on` (which hub card(s), if any, resolve to it — `[]` for orphans) and `is_orphan`. Unlike the old `cpt_orphans` array, pass 2 now runs against **all 62** CPT posts rather than just the 38 that resolve to a hub card, so the 24 orphans in this file get a real detail-page scrape (SEO, breadcrumb, body text) too — their `/tie-up-list/<slug>/` pages 200 fine, they just were never visited before. `ils_tie_up_list.json` degrades to `{ present: false }` under `--from-list`, since that mode never fetches the REST CPT list.

`ils-about-us-scraper.js` covers three pages and two unrelated datasets. Awards: the 26 `.award-box` cards on `/accreditations-awards/` are anchors in a single owl-carousel, and **each card carries two image URLs** — the `<img src>` is a small web-optimised crop, while the *parent* `a[data-lightbox="example-set"]`'s `href` is the full-resolution scan the lightbox popup shows (one shared `data-lightbox` group is why the popup is a carousel over all 26). The anchor wraps the card, so `$('.award-box').find('a')` finds nothing — use `.closest('a')`. Like press/media, the join to WP REST is **by featured image** (card `<img src>` == the post's `featured_media` `source_url`, all 26 distinct) rather than by title, because two distinct posts (12602/12605) share the title "Leading Chain of Multi Specialty Hospitals" and a title join silently loses one. The full-resolution image is an ACF field REST never exposes, so it is resolved back to its media record by filename — batched `?slug[]=` (stripping the `-scaled` / `-e<timestamp>` suffixes WP appends) plus a `?search=` fallback for the 2 whose attachment slug was renamed on re-upload, always confirmed on exact `source_url`. `/about-us/` renders a 14-card subset of the same awards; that is `appears_on`, not a second source. `/award/<slug>/` pages 200 but reuse the CSR template with no body copy and re-show the *small* thumbnail, so pass 2 takes their SEO block and records `detail_page_has_no_body_content`. Members: they live on **two** pages with identical `.leadership-team-sec .team-box` markup — `/about-us/` has the 3 that are also a `leadership-team` CPT (bio behind a bootstrap modal), `/investor/board-of-directors/` has all 10 board members (no modal, no bio, no CPT, 6 on a shared placeholder portrait, designations prefixed `Designation: ` and one carrying a malformed `&kmp;` entity).

### Record defects, never work around them

Every scraper emits a per-record `seo_issues` / `issues` array and prints an aggregate tally at the end of the run (see `status.txt` for a past run's tallies). Codes like `og_image_generic_logo`, `twitter_url_placeholder`, `canonical_points_to_homepage`, `randomized_faq_schema`, `count_mismatch` are the deliverable, not noise — the point of the exercise is auditing the site's SEO. Unparseable JSON-LD is kept verbatim under `_parse_error`/`_raw`; blocks that only parse after control-char repair are tagged `_repaired`.

## Site-specific gotchas encoded in the code

Each scraper's header comment documents the quirks of its content type in detail — **read it before changing selectors**. The load-bearing ones:

- **Meta tag ordering differs by content type.** Blog posts ship the misconfigured AIOSEO block first (homepage values) and the correct theme block second; department/doctor/procedure pages ship the theme block first and AIOSEO second. `extractSeo` resolves og/twitter *last-non-empty-wins*, which is right for posts and right for title/description/canonical elsewhere — but wrong for `og:image`, which AIOSEO overwrites with the generic logo. Those scrapers therefore keep a first-wins reading alongside as `seo.og_theme` / `seo.twitter_theme`, via a locally duplicated `resolveFirst`.
- **`<title>` is unreliable.** Posts ship an empty one; taxonomy archives ship a *listed post's* title leaking out of the theme loop. Hence `meta_title` (raw) plus `meta_title_resolved` (a fallback chain), and `title_leaks_post_title` on archives.
- **`slug` is the identity key**, never `name` — health package names are duplicated across hospital variants at different prices.
- **Sections skipped on purpose** and listed in the file headers (randomized FAQ card triples, byte-identical testimonial carousels and lead forms, the randomized "Other FAQs" strip on `/faq-lists/` pages, the randomized "Other testimonials" strip on `/testimonial/<slug>/` pages). Do not "restore" them; the randomized ones make every rerun diff for no reason.
- **The "Other Health Packages" strip is the exception — it is captured, not skipped.** It genuinely is boilerplate (the same four cards on all 35 detail pages, each of those four listing *itself*), but unlike the randomized strips it is stable, so recording it costs nothing and its slugs are the links the site actually renders. It lands in `other_health_packages` / `other_health_packages_slugs` and is flagged `other_packages_strip_is_boilerplate` + `other_packages_includes_self`, with `other_packages_stale` comparing each strip card's parameter count and prices back to the listing card it was hand-copied from. The relations worth linking are computed separately into `related_packages` (`variants` = the same package at another unit, `same_hospital` = everything else sold where this one is), keyed on the **normalized name** rather than the slug — `cancer-screening-male`/`-female` are Raipur packages carrying no `-raipur` suffix, so suffix-stripping groups them wrongly.
- **The health package "N Parameter" count exists for only 15 of the 35, and that is the site's gap, not the scraper's.** The other 20 (all 15 `-raipur` variants plus cancer-screening-male/female, renal-screening, care-of-senior-citizen, gold-health-checkup) have no count anywhere public: no `<p>` on the listing card, `acf: []` from WP REST, nothing on the detail page, and no MonsterInsights `dataLayer_content` blob. `parameter_count` stays null with `parameter_count_source: null` and `missing_parameter_count`; do not estimate it from `tests_count`, which counts test *groups* (34 parameters vs 12 groups on complete-cardiac-care) — hence `parameter_count_below_test_count` rather than an equality check. The listing card *is* held to its own teaser, though: 3 shown + "+N More" must equal the detail page's test count, and `teaser_count_mismatch` catches the 5 where it doesn't.
- **Key procedures grew 115 -> 173, and the 58 newer pages use a different head template.** The original 115 ship the two meta blocks described above (theme first, AIOSEO second, 4 ld+json blocks); the 58 added after Jul 2026 ship **one** AIOSEO block and no theme block at all — 1 ld+json, a correct self-referential canonical, no meta description, and no `MedicalProcedure` node. So `no_post_specific_schema` / `no_post_specific_meta` / `no_medical_procedure_schema` each tally 81 (23 of the originals + all 58), while the AIOSEO-only codes (`randomized_faq_schema`, `twitter_url_placeholder`, `og_image_generic_logo`) stay pinned at 74 and `json_ld_repaired` at 88 — those three never fire on a new-template page. `missing_icon` is 86 (51 of the new ones have `<img src="">`). A tally where the 74/88 group moved means the *old* pages changed; a tally where the 81 group moved means the split shifted.
- **The cache never expires, so a plain re-run is a replay, not a re-scrape.** `fetchHtml`/`fetchJson` serve any existing `.cache/` key unless `--refresh` is set (`scrape-lib.js:87`). That is the point while iterating on parsers, but it means a months-old cache silently reproduces a months-old dataset: the key-procedure scraper emitted 115 records for weeks after the site reached 173, and nothing complained. `ils-key-procedure-scraper.js` now diffs its listing slug set against the REST collection's on every non-narrowed run (`reconcileListingWithRest`) and warns `rest_missing_from_listing` / `listing_missing_from_rest`; the other two-pass scrapers have no such guard yet. Before trusting any dataset, check its `.cache/` mtime, or cross-check its count against `ils_sitemap.json`'s matching section, which is what caught this one.
- **Testimonial video embeds ship broken markup.** `.video-box a.play-video`'s `href` attribute isn't a URL — it's the raw, unescaped `<p><iframe src="...">` markup pasted in verbatim. This breaks cheerio's own re-parse of the anchor (for the 21 Facebook-hosted ones the reconstructed DOM loses the `src` entirely, splitting it across bogus attributes), so `ils-testimonial-scraper.js` regexes the *raw* HTML string for the iframe `src` instead of anything cheerio has parsed — read `extractVideo()` before touching this selector.
- **Extracted HTML is whitespace-normalized** (`normalizeHtmlWhitespace`) so it round-trips through JSON readably. This is rendering-identical only because the corpus contains no `<pre>`/`<code>`/`<textarea>`.
- **Job detail fields ship doubly-nested markup.** Each field in `section.job-sec-details` (Education Qualification, Specialty, Experience, Job Description) is a `<p>` wrapper with WYSIWYG content — itself a `<p>` or `<ul>` — pasted straight inside it. Since `<p>` can't contain block content, the parser auto-closes the wrapper on the inner tag, leaving an empty `<p>`, the real content, and a second orphaned empty `<p>` as three siblings. `ils-career-scraper.js`'s `extractJobFields()` filters to non-empty siblings rather than assuming the value is always the first `<p>` child (see its header comment).
- **Every job detail page ships an identical, wrong breadcrumb** — "Get in Touch - Investor - `<job title>`" — hardcoded in the template regardless of the actual job. Recorded verbatim plus a `broken_breadcrumb_hardcoded` issue on every record, not corrected.
- **Insurance tie-ups have no hospital dimension anywhere on the site, and Howrah has no corporate ones.** Corporate tie-ups genuinely are per-unit (Saltlake 2, Dumdum 5, **Howrah 0**, Agartala 12, Raipur 8 — `div#corpTab3` is a literally empty div upstream, recorded as `corporate_tab_empty` / `hospital_has_no_corporate_tieups`, not filled in from a sibling tab). Insurance is not: `#insuranceTieUps` carries no tab, class or data attribute, and the "Insurance Tie Ups" carousel on `/hospital/<slug>/` (`section#priCITP` → `ul#slide_tie_up li.slid-item > img`) renders the **same 13 logos in the same order on all five units** — a teaser subset of the 38, verified every run by pass 2b and recorded once as `hospital_insurance_carousel` rather than as five duplicate lists. So insurance records are emitted with all five hospitals under `hospital_scope: "site_wide"` plus `insurance_not_hospital_scoped` + `hospital_scope_inferred_all_units`: queryable per hospital, never claiming a per-hospital source. The insurer/TPA split is likewise **inferred, not published** — the 38 are one unbroken `<ul>`, split at the single alphabetical restart (23 insurers, then 15 TPAs), cross-checked against the `\bTPA\b` name test, and tagged `tpa_classification_inferred` on every record; a future disagreement between the two signals falls back to the name test and raises `tpa_classification_disagrees`.
- **The gallery CPT's SEO is uniform and uniformly wrong, so its tally is all-85s by design.** Every `/gallery/<slug>/` page ships a single AIOSEO block and no theme block, so `no_post_specific_schema` / `no_post_specific_meta` are structural and dropped from the tally (as in `ils-gallery-scraper.js` and `ils-press-media-scraper.js`); the canonical is self-referential and correct, but `og:image` is the generic `/2023/10/logo.png` rather than the post's own featured image, there is no meta description, no `og:description`, no `twitter:description` and no `twitter:url` anywhere, and all 84 media records have empty alt text. `og_image_generic_logo`, `og_image_ignores_featured_image`, `missing_meta_description`, `missing_og_description`, `missing_twitter_description`, `missing_twitter_url`, `breadcrumb_points_to_blog`, `no_body_content`, `title_duplicated_in_heading` and `featured_image_missing_alt` therefore each tally **85** on a clean run — a count below 85 means the site changed, not that the scraper improved.

## Output files

`ils_*.json` are the full scraped datasets; the bare `departments.json`, `doctors.json`, `key_procedures.json`, `health_packages.json`, `events.json`, `opd_schedules.json`, `faqs.json`, `testimonials.json`, `careers.json`, `csr.json`, `press_and_media.json`, `tie_ups.json`, `gallery_posts.json` are the small pass-1 / index files. `ils_events.json` is the full event dataset; `ils_opd_schedules.json` is the per-doctor OPD schedule (source of the `timings` merged into `ils_doctors.json`). `ils_faqs.json`, `ils_testimonials.json` and `ils_press_and_media.json` are the array-backed datasets that are objects rather than arrays — `{ hub, categories, standalone_questions }`, `{ listing, testimonials }` and `{ hub, items }` respectively (the `hub`/`listing` key is null when the run replays a `--from-list` index, since that page is then never fetched). `ils_gallery.json` is also a single object rather than an array (`{ url, title, breadcrumb, image_count, images, seo, seo_issues }`), but for the opposite reason — there is exactly one page, not a hub over many. `ils_gallery_posts.json` is the CPT behind that page and an object as well (`{ url_source, rest_url, post_count, posts, blog_sidebar_boilerplate, sitemap_audit, gallery_page_audit, issue_tallies }`) — each post carries `gallery_page_position` / `gallery_page_title` (its row on `/gallery/`) and `sitemap_position` / `sitemap_global_position` alongside the usual `seo` / `seo_issues`, and the byte-identical blog sidebar is stored once at the top level rather than 85 times; `sitemap_audit` / `gallery_page_audit` are null under `--from-list` (their inputs live in the index) and `{ present: false }` when the sibling dataset is missing. `ils_about_us.json` is likewise an object, not an array — the three page-level SEO blocks (`/about-us/`, `/accreditations-awards/`, `/investor/board-of-directors/`), an `awards_carousel` summary of the lightbox popup, the `members` and `awards` arrays also written standalone to `ils_members.json` / `ils_awards.json`, the sitemap audit, and `issue_tallies`. Each `ils_health_packages.json` record additionally carries `parameter_count_source`, `more_tests_count`, the verbatim `other_health_packages` / `other_health_packages_slugs` / `other_health_packages_view_more_url` strip capture, and the computed `related_packages` (`{ name_key, variants, same_hospital }`). `ils_tie_ups.json` is an object too: `{ hub, hospitals, corporate, insurance, cpt_orphans, hospital_insurance_carousel, issue_tallies }` — `hospitals` is the per-unit roll-up (id, name, its `corporate_names`, and `insurance_count` with `insurance_scope: "site_wide"`), `corporate` and `insurance` are the flat record lists, and `hub` / `hospital_insurance_carousel` are null under `--from-list` since those pages are then never fetched (`hospitals` is rebuilt from the records themselves so it survives the replay). The same scraper additionally writes `ils_tie_ups_corporate.json` (`{ hub, hospitals, records, issue_tallies }`, `records` = the same `corporate` array) and `ils_tie_ups_insurance.json` (`{ hub, records, hospital_insurance_carousel, issue_tallies }`, `records` = the same `insurance` array) as standalone per-kind files, plus `ils_tie_up_list.json` — the `tie-up-list` CPT itself, `{ rest_url, post_count, posts, issue_tallies }`, all 62 posts each carrying `appears_on` / `is_orphan` and (unlike the old `cpt_orphans` array) a full pass-2 detail scrape even for orphans; it is `{ present: false }` under `--from-list`. `ils_sitemap.json` is an object as well (`{ url, title, breadcrumb, section_count, entry_count, sections, entries_flat, duplicate_urls, seo, issues, xml_audit, dataset_audit, issue_tallies }`) — `sections[].entries[]` is canonical and `entries_flat` repeats the same rows as compact `{ global_position, section_position, category, position, name, url }` tuples so the sequence is verifiable end to end; `xml_audit` / `dataset_audit` are null under `--no-xml` / `--no-dataset-check`. `ils_blogs_v2.json` is the current blog dataset (it has the `content` field); `ils_blogs.json` and `ils_blogs_2.json` are earlier runs without it. `saltlake.html` is a saved sample page kept for selector work.
